Naming a file is a tiny act of optimism. You are assuming that future you will understand what present you meant. A little consistency makes that a much safer bet, particularly when a project has more versions than anyone expected.

## Start with the date

This example demonstrates Markdown’s technical typography. It is a sample workflow rather than a claim about Neil’s actual working methods.

Use a date such as `2026-08-29`, then a project name, then a description. Dates written from largest unit to smallest sort naturally in a folder.

```text
2026-08-29_project-name_edit_v01
2026-08-29_project-name_edit_v02
2026-08-30_project-name_review_v01
```

### Keep the vocabulary small

| Part    | Example    | Purpose                    |
| :------ | :--------- | :------------------------- |
| Date    | 2026-08-29 | When this version was made |
| Project | short-film | What it belongs to         |
| Stage   | review     | What it is for             |
| Version | v02        | Which iteration it is      |

Avoid making the system so precise that you stop using it. A good naming convention is one that survives a busy afternoon.

## Write a note for later

A plain text file next to the work is often enough. Record a decision, an export setting or the location of a missing asset. Keep it short enough to read at a glance.

The goal is not a perfect archive. It is spending a little less time searching and a little more time making things.
